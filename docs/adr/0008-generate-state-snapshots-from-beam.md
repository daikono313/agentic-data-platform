# 0008: 状態（定期スナップショット）の値の求め方を BEAM の measure に書き、生成器が SQL を作る

- 日付: 2026-10-22
- ステータス: Proposed
- 関連: [#138](https://github.com/daikono313/agentic-data-platform/issues/138)、#134、#46、design-doc の R5・R26、ADR [0004](0004-cleansing-layer.md)・[0007](0007-map-each-concept-to-one-model.md)
- 見直し: 「最後の値」「積み上げ」で表せない状態の要求（例: 期間の平均残高、段階を経て進む状態）が来たとき、または源泉に期首の残高の記録が入ったとき

## 背景

BEAM の `story_type: recurring`（定期的に測る状態。月末在庫など）は、periodic snapshot の fct になる（[modeling-conventions](../modeling-conventions.md)）。しかし、生成器は作れない。`DesignBuilder._fact` が「定期スナップショット（recurring）は MVP では生成できません」を確定前の課題にしている（`backend/src/adp/design/builder.py`）。

在庫の要求（`beam/inventory_status.yml`）は、入出庫の fact（`fct_stock_movements`）で受けた。月末在庫は gap にして後回しにしている。

源泉 `raw.inventory` の 1 行は在庫の動きで、`quantity` の意味は `movement_type` で変わる（`warehouse/scripts/generate_sample_data.py` の `_inventory`）。

- receipt（入庫）: 増えた数（プラス）
- transfer_out（移動出庫）・disposal（廃棄）: 減った数（マイナス）
- count（棚卸）: 数えた在庫数そのもの。増減ではない

増減と棚卸は足せない。そのため、指標 `monthly_stock_change_qty` は棚卸の行を filter で除いている（`warehouse/models/marts/fct_stock_movements.yml`）。

月末在庫を出すには、行をまたぐ計算が要る。店舗 × 商品ごとに、時刻の順に増減を積み上げ、棚卸で数え直した数に置き換え、記録の無い月は前の月の値を引き継ぐ。

この計算を書ける場所は限られている。

- クレンジング層は 1 テーブルの中の整形だけで、計算・結合はしない（ADR 0004）。積み上げは計算で、記録の無い月の引き継ぎには暦（`dim_date`）との結合が要る。
- BEAM の `SourceRef.expr` は 1 行ごとの式だけで、集計・ウィンドウ関数・サブクエリは受け付けない（`_check_row_expr`、#46）。

v5（オーナーの指示、2026-10-12）で、状態をヒアリングから生成まで通しで扱う（#138）。

2026-10-22 に `warehouse/data/dev.duckdb` で確かめたこと:

- `raw.inventory` は 10,000 行。期間は 2024-01-01〜2025-12-31。
- 店舗 × 商品の組は 2,272。そのうち最初の記録が棚卸の組は 548（約 24%）、棚卸が 1 回も無い組は 773（約 34%）。
- 同じ店舗・商品・時刻の行は無い。

期首の在庫は記録の外にある。生成スクリプトでは、組ごとに 0〜30 の乱数で、源泉には残らない。

## 判断の基準

- **安全の境界を保つこと。** LLM が書いた SQL を生成物に入れない。BEAM の値は許可リストで検査できる形にする（#46、ADR 0004）。
- **決定的で、テストで確かめられること。** 同じ BEAM から同じ SQL ができる。具体例から unit test を作れる。
- **ビジネスユーザーが答えられること。** 技術の言葉（窓関数、semi_additive）を聞かずに決められる（R1）。
- **既存の決定と合うこと。** 集計は Semantic Layer に一元化する（R5）。概念とモデルは 1 対 1（ADR 0007）。

## 検討した選択肢

### 案 A: measure に状態の求め方（`state`）を書き、生成器が決まった形の SQL を作る（採用）

recurring のイベントの measure に、次を構造化した値で書く。

- 求め方: 記録が時点の値そのものなら「期間の最後の値」（`last_value`）、増減の記録なら「積み上げ」（`running_total`）。
- 置き換える行: 積み上げのとき、値を数え直した数に置き換える行。BEAM の絞り込みと同じ形で書く（例: `movement_type` が `count`）。

記録の無い期間は、前の期間の値を引き継ぐ。これは BEAM に書く項目ではなく、生成器が常にそうする。

スナップショットの粒度は、時間軸（When）の `time_grain`（月など）にする。区切りは、粒度のキーから When を除いたもの（店舗 × 商品）。同じ時刻の行は、源泉の主キーの順に処理する。

- 良い点:
  - SQL を書かずに値だけを書くので、ほかの BEAM の項目と同じく検査できる。
  - 2 種類の源泉（すでに時点の値の記録、増減の記録）を同じ仕組みで扱える。
  - 具体例（店舗・商品・月末・在庫数）から、入力の履歴と期待値を作って unit test にできる。
  - インタビューでは「その時点の数そのものですか、増えた・減った数ですか」「数え直した記録（棚卸）はありますか」と、平易に聞ける。
- 悪い点:
  - BEAM のスキーマが変わる。JSON Schema と frontend の型を生成し直す。
  - 求め方は 2 種類に限られる。ほかの求め方が要れば、生成器とスキーマを足す。
  - 期首の値は記録の外にあるので、最初の「置き換える行」（棚卸）より前の期間は値を出さない。2026-10-22 の源泉では、棚卸が 1 回も無い 773 組（約 34%）は値が出ない。

### 案 B: 計算をクレンジング層か、手で書く `int_` モデルに置く

- 良い点: 生成器を変えずに済む。SQL の自由度が高い。
- 悪い点:
  - クレンジング層に置くと、計算と暦との結合を入れることになり、ADR 0004 を覆す。
  - 手で書く `int_` は、BEAM から生成する流れから外れる。要求ごとに人が SQL を書くことになり、生成の価値が無くなる。
  - 生成エージェント（LLM）に書かせると、安全の境界（#46）が崩れる。そのため採らない。

### 案 C: 増減の fact のまま、MetricFlow の cumulative 指標で積み上げる

- 良い点: fct を増やさない。
- 悪い点:
  - 棚卸での置き換えを表せない。cumulative は足し上げだけで、途中で値を置き換えられない。
  - 積み上げた結果は時点の値だが、cumulative 指標の結果を、さらに期間の終わり（月末）で切る手段が無い。そのため採らない。

### 案 D: 棚卸の行だけを、MetricFlow の時点の値（semi_additive）として集計する

棚卸の行に絞った measure を semi_additive にし、`non_additive_dimension` を時間軸にして、期間の最後の値を取る。生成器は変えない。

- 良い点: 今の生成器と Semantic Layer だけで作れる（#134 で semi_additive の集計は実装済み）。
- 悪い点:
  - 棚卸と棚卸の間の入出庫が反映されない。月末在庫ではなく「最後に数えた数」になる。
  - 棚卸の無い月は値が出ない（引き継げない）。2026-10-22 の源泉では、棚卸が 1 回も無い組が約 34% ある。そのため採らない。

## 決定

案 A を採る。判断の基準の「安全の境界を保つこと」と「決定的で、テストで確かめられること」を優先した。求め方が 2 種類に限られることは、要求が来たときに生成器を足して広げる。

periodic snapshot の fct は、状態の記録の粒度（区切り × 期間の終わりの値）を持つ fact で、指標の集計ではない。期間をまたぐ集計（平均・合計）や、店舗・カテゴリへのまとめは Semantic Layer に残す。そのため、集計を Semantic Layer に一元化する R5 と、集計済みの fct を作らない ADR 0007 の案 B の理由とは矛盾しない。

## 結果

- 良い影響:
  - 月末在庫のような状態の指標を、インタビューから PR まで通せる。
  - `fct_stock_movements` の棚卸を除く回避策と、月末在庫の gap を外せる。
- 悪い影響・トレードオフ:
  - 最初の棚卸より前の期間は値が出ない。生成した PR の未解決事項に書く。
  - スナップショットの行数は「区切り × 期間」で増える。
  - 同じ時刻に置き換える行と増減の行があると、結果が源泉の主キーの順に依存する。
- 後続の作業・ADR（#138）:
  - オントロジーに状態の概念の種類（`state`）を足す。同じ源泉から出来事の fact と状態の fact を作れるよう、ADR 0007 の 1 対 1 を保ったまま、概念を分ける。
  - 暦は、ADR 0007 の案 D のとおり概念にしない（`dim_date` は共通のモデルのまま）。変えるなら別の ADR にする。
  - BEAM の `state` は任意の項目なので、`schema_version` は上げない。JSON Schema と frontend の型（`frontend/src/generated/`）は生成し直す。
  - modeling-conventions に、periodic snapshot の列名・テストを書く（T3）。
  - インタビューで聞くことを足す（`docs/knowledge/interview.md`、C10）。

## 守らせ方

- 生成を止めている確定前の課題: `backend/tests/design/test_builder.py` の `test_duplicate_columns_and_periodic_snapshot_are_blockers`。この ADR に沿って生成器を作る PR で、生成できることを確かめるテストに置き換える。
- 前提として既にある検査: 時点の値（semi_additive）は recurring のイベントにだけ置ける（`backend/tests/beam/test_beam.py` の `test_additivity_rules`）。この ADR の決定を守らせるものではない。
- `state` の検査、生成した SQL の unit test、手で書いたリファレンス fct との突合は、生成器を作る PR で足す。それまでは「無し」。
