# 0005: 実データへの切り替え（準備）と、個人情報の扱い

- 日付: 2026-10-11
- ステータス: Proposed（個人情報の扱いはオーナーの承認待ち。#81）
- 関連: #81、design-doc の Privacy、guardrails §3

## 背景

いまは合成のサンプルデータ（DuckDB のファイル）だけで動く。実データ（BigQuery など）に切り替えるときに、
どこを差し替えるか・個人情報をどう扱うかを先に決めておく。実際の接続はこの ADR の範囲外。

## 決定（準備としてやったこと）

- **接続先の決め方を 1 か所に**（`adp.warehouse`）: `ADP_WAREHOUSE`（環境変数か .env。既定は duckdb）。
  未対応の値ならアプリの起動時に止める。DuckDB のファイルの場所は `warehouse_db()` に集めた。
- **個人情報の列は値を出さない**: 源泉のプロファイル（画面）とソースカタログの tool（インタビューの
  エージェント）で、個人情報の列は件数（行数・NULL・種類の数）だけを出し、値（最小・最大・よく出る値・
  分布）は出さない。個人情報の列は、dbt の sources の列の `meta: {pii: true}`、または列名からの推定
  （顧客名・氏名・かな・メール・電話・住所・郵便番号・生年月日など）。`meta: {pii: false}` で推定を外せる。
  集計の区分（都道府県・地方・性別など）は出す。

## 切り替えの手順（実データに接続するとき）

1. dbt のアダプタ（例: dbt-bigquery）とプロファイル（`warehouse/profiles.yml` の target）を追加する。
   ライセンスを確認する（Apache-2.0）。
2. ソースカタログ（`adp.catalog.Catalog`）を、INFORMATION_SCHEMA を読む実装に差し替える。
   読み取り専用の権限のサービスアカウントだけを使い、件数・値の取得はサンプリングと上限を付ける。
3. 生成ジョブの検証（`prepare_warehouse`）は、DB をコピーできないので、ブランチごとのデータセット
   （スキーマ）に dbt build する。終わったら消す。
4. MetricFlow と dbt Charts の接続を、同じプロファイルにする。描画画面のクエリには上限を付ける。
5. サンプルデータの生成（`make sample-data`）は使わない。
6. 個人情報の列の `meta: {pii: true}` を sources に付け、推定に漏れが無いかをプロファイル画面で確かめる。

## 検討した代替案

- **値をハッシュ化して見せる**: 値の分布を見たい用途はあるが、少ない値はハッシュから推測できる。
  まずは見せない。

## オーナーに決めてほしいこと（承認待ち）

- 上の「個人情報の列は値を出さない」範囲で十分か（列名の推定の対象、集計の区分を出してよいか）
- 実データでは、LLM（インタビュー・取り込みのエージェント）に渡すメタデータ（列名・説明・件数・
  個人情報でない列のよく出る値）の範囲をこのままでよいか
