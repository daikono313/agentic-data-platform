# ADR（Architecture Decision Records）

[design-doc.md](../design-doc.md) の確定後に、その決定（Resolved issues）を変える、または新しく重要な決定をするときに書く。書き方は [architecture-decision-record](https://github.com/architecture-decision-record/architecture-decision-record) のベストプラクティス（Nygard と MADR のテンプレート）に沿う。

- **ADR は人間の決定の記録。** AI が `Proposed` で下書きしてよいが、`Accepted` にするのはオーナー（certificate の T3）。
- 書いたら、design-doc の Resolved issues / Open issues も更新する。

## 書くとき・書かないとき

書くのは、後から来た人（人間も AI も）が「なぜこうなっているか」を知る必要がある決定。

- 書く: design-doc の決定を変える、構成・依存（ライブラリ・外部サービス）を選ぶ、信頼の境界やデータの扱いを決める、複数のモジュールにまたがる約束を決める
- 書かない: アーキテクチャに関わらない決定、小さく閉じた決定（1 つのモジュールの中で済み、戻しやすい）、規約（modeling-conventions など）や design-doc に既に書いてあること、一時的なもの（回避策・PoC・実験。PoC の結果は、それで決めた ADR に書く）

## 書き方

- **1 つの ADR に 1 つの決定。** 決定から生まれる小さな決定は、別の ADR にして「結果」から指す。
- **「何を」より「なぜ」。** 背景（状況・制約）、判断の基準、選択肢ごとの良い点と悪い点を書く。
- **時点を書く。** バージョン・計測値・費用など、時間で変わる値には、いつの値か（日付・バージョン）を添える。
- **守らせ方を書く。** 決定が守られていることを確かめるテスト・検査（fitness function）を書く。無ければ「無し」と理由を書く。
- **ファイル名**: `NNNN-<決定を表す動詞句>.md`（英小文字の kebab-case。例: `0006-choose-warehouse-adapter.md`）。番号は連番で振り直さない。0001〜0005 は名詞句のままにしている（コードやテストから参照しているため）。

## ステータスと変更のしかた

```
Proposed → Accepted → Superseded by NNNN / Deprecated
```

- `Proposed`: 下書き。AI が書いてよい。
- `Accepted`: オーナーが承認した。承認の前に、問題がはっきり書かれているか、選択肢を比べたか、トレードオフと守らせ方が書かれているかを確かめる。
- `Superseded by NNNN`: 決定を変えた。**新しい ADR を書き**、古い ADR のステータスをこれにする（本文は残す）。
- `Deprecated`: 決定が要らなくなった（機能を消したなど）。理由を「追記」に書く。

Accepted の後は、**本文（背景・選択肢・決定）を書き換えない。** 決定の後にわかったこと（実際に使った結果、バージョンを上げた、後の ADR が一部を変えた、など）は、末尾の「追記」に日付を付けて足す。決定そのものを変えるときは、新しい ADR にする。

## 見直し

ADR ごとに「見直し」の時期か条件を書く（例: dbt-core のパーサーが直ったら、実データに切り替えるとき）。その時が来たら、追記するか、新しい ADR で置き換える。

## テンプレート

```markdown
# NNNN: <決定を表すタイトル>

- 日付: YYYY-MM-DD（決定した日）
- ステータス: Proposed | Accepted（YYYY-MM-DD、<承認した人・場所>） | Superseded by [NNNN](NNNN-....md) | Deprecated
- 関連: #<issue>、design-doc の R<n> / O<n>、ADR NNNN
- 見直し: <時期か条件>

## 背景

<いまの状況、解決したい問題、制約。なぜいま決めるか。>

## 判断の基準

- <この決定で重視すること（安全・速さ・保守のしやすさ・既存の決定との整合など）>

## 検討した選択肢

### 案 A: <名前>（採用）

- 良い点: …
- 悪い点: …

### 案 B: <名前>

- 良い点: …
- 悪い点: …（採らない理由）

## 決定

<採る案と、その理由（判断の基準のどれを優先したか）。>

## 結果

- 良い影響: …
- 悪い影響・トレードオフ: …
- 後続の作業・ADR: …

## 守らせ方

- <決定が守られていることを確かめるテスト・検査（例: `make dbt-build` の検査、`tests/...` のテスト）。無ければ「無し」と理由>

## 追記

- YYYY-MM-DD: <決定の後にわかったこと・変わったこと>
```
