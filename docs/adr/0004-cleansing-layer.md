# 0004: staging をクレンジング層にし、定義から生成する

- 日付: 2026-10-11
- ステータス: Accepted
- 関連: #68、#69、modeling-conventions の「レイヤー」
- 見直し: 定義に書けない種類のクレンジング（1 テーブルで完結しない処理など）が必要になったとき

## 背景

源泉を追加したとき、fact / dim の前に、前後の空白・空文字・表記ゆれ・重複・テスト用の行などを片付ける層が要る（オーナーの要望）。これまでの staging（`stg_*`）は「列名の整形と型変換のみ」で、手書き（生成時は列をそのまま選ぶだけ）だった。何をクレンジングするかを、源泉ごとに設定として決められるようにしたい。

## 判断の基準

- 源泉ごとに、何をクレンジングするかを設定として決められる
- 生成エージェントやユーザーの入力（#69）から作っても安全（任意の SQL・Jinja を書けない。許可リストで検査できる）
- 既存の生成器・規約の「stg を読む」前提を崩さない
- 同じ定義から同じ結果を作る（決定的。LLM を使わない）

## 検討した選択肢

### 案 A: staging をクレンジング層にし、構造化した定義から生成する（採用）

- 良い点: 定義は構造化した項目だけなので、許可リストで検査できる。層は増えない。
- 悪い点: 定義に書ける処理に限られる。staging の責務が広がる。

### 案 B: dbt のマクロでクレンジングを共通化する

- 良い点: dbt の標準的なやり方で、自由度が高い。
- 悪い点: 定義が SQL・Jinja になり、許可リストで検査しにくい。生成エージェントやユーザーの入力から作るには危ない。

### 案 C: staging とは別に `cln_*` 層を足す

- 良い点: staging の責務を変えない。
- 悪い点: 層が増え、既存の生成器・規約の「stg を読む」前提を全部変える必要がある。1 テーブルで完結する処理なので、staging に含めれば足りる。

## 決定

案 A を採る。

- 源泉ごとの**クレンジングの定義**（`warehouse/cleansing/<schema>.<table>.yml`）と、型ごとの既定（`warehouse/cleansing/_defaults.yml`）から、`stg_<table>.sql` と `.yml`（テスト）を**決定的に**生成する（`adp.cleansing`。LLM を使わない）。生成物の先頭に印を入れ、手で編集しない（`make cleansing`）。
- 定義に書けるのは構造化された項目だけ:
  - 列: 型変換（try_cast。許可した型だけ）、タイムゾーン、trim、大文字小文字、空文字を NULL、値の対応表、列名の変更・削除、日付・月・年の切り出し、accepted_values / not_null のテスト
  - テーブル: 主キー（unique / not_null）、重複の除去（キーと優先順）、除外する行（is_null / in / equals）
  - 任意の SQL・Jinja は書けない（値の `{` `}` `\` と制御文字を拒否、識別子は英小文字に限る）
- 除外の条件の列が NULL の行は除外しない（`not coalesce(条件, false)`）。値の対応表・trim などは、型変換の後の型に合うものだけ書ける（検証で拒否する）。
- staging の責務を「列名の整形と型変換」から「1 テーブル内で完結するクレンジング（行の除外・重複の除去を含む）」に広げる。計算・結合はこれまでどおり staging ではしない。
- 生成パイプラインが新しい源泉の staging を作るときは、定義があればそれを使い、無ければ既定の定義（キーだけ）を一緒に作る。生成エージェントは定義と生成物を書き換えられない（guard）。
- 源泉のプロファイル画面から、定義の雛形（主キー候補、値の種類の少ない列の accepted_values、日時の文字列の型変換、キーが重複していれば更新日時での重複除去）を出す。

## 結果

- 良い影響: 源泉ごとのクレンジングが設定として PR でレビューできる。stg は定義の生成物になる。
- 悪い影響・トレードオフ: 既定で文字列の列に trim と空文字の NULL 化をかけるので、以前の手書きの stg と「同じ結果」なのはサンプルデータ（前後の空白・空文字が無い）での話で、実データでは結果が変わりうる（それがクレンジングの目的）。
- 後続の作業・ADR:
  - 既存の 6 つの stg は定義から再生成した（stg の無かった 3 つの源泉 payments / shipments / returns は、取り込みのときに定義を作る）。
  - `_stg_models.yml` は、モデルごとの生成物（`stg_<table>.yml`）に置き換えた。
  - 規約（modeling-conventions）と guardrails を更新した。

## 守らせ方

- `make dbt-build`（CI）で定義を検証する: 源泉の列との矛盾、生成物が最新か、定義の無い stg（手で書いたもの、定義を消した後の残り）が残っていないか（`backend/src/adp/cleansing/check.py`）。型変換で NULL になる値があれば警告する。
- 生成エージェントのガードで、定義と生成物を書き換え不可にしている。
- `backend/tests/cleansing/test_cleansing.py` の `test_repository_definitions_reproduce_previous_staging`: 以前の手書きの stg と結果が同じこと（サンプルデータで）。
