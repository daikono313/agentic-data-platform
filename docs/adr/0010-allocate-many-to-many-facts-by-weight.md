# 0010: 多対多の切り口は、按分した fct（出来事 × 値の粒度）で持つ

- 日付: 2026-10-22
- ステータス: Proposed
- 関連: [#143](https://github.com/daikono313/agentic-data-platform/issues/143)、design-doc の R5・R27、ADR [0007](0007-map-each-concept-to-one-model.md)・[0008](0008-generate-state-snapshots-from-beam.md)
- 見直し: MetricFlow が、ブリッジを通る結合（fan-out join）と重み付けに対応したとき。または、按分しない見方（「影響のあった売上」の全額）の要求が続いたとき

## 背景

今の BEAM では、出来事のディメンションは fct の 1 つの外部キーの列になる（`Dimension.fact_key`）。1 つの出来事に複数の値が付く切り口（例: 1 注文に複数のプロモーション）は表せない。

生成器が探す結合は、ベースのテーブルからの多対一の経路だけ。そのため、多対多の源泉の列を切り口にすると、確定前の課題（結合できない）で止まる。

v5（オーナーの指示、2026-10-12、#143）で、複数値の切り口の要求から、二重計上しない指標を作る。

2026-10-22 に、`warehouse/` の複製で確かめたこと。版は dbt-core 1.12.5、metricflow 0.213.0（dbt-metricflow 0.15.0）。

- **サンプルデータに多対多は無い。** `raw.orders.promotion_id` は 1 列で、1 注文に 1 件まで。
- **ブリッジを通る結合は使えない。** 確かめるため、注文 × プロモーションの源泉（5,670 行。2 件付いた注文が 381 件）を複製の中で作った。
  - MetricFlow は、fct からブリッジへの外部キー同士の結合を拒否する（「fan-out join support is pending」）。そのため二重計上はしないが、ブリッジを通して金額の合計は出せない。
  - ブリッジの entity を `unique` と偽って宣言すると、`mf validate-configs` は通るのに結合して二重計上する。按分しない合計は 1,074,412,003 で、正しい売上 1,061,675,323 より 12,736,680 多い。
- **按分した fct は、普通の fct として動く。** 明細 × プロモーションの粒度で、金額に重み（1 注文のプロモーションの数で均等に割る）を掛けた。
  - 按分した金額の合計は、元の売上と一致した（1,061,675,323）。
  - 元の明細の fct の主 entity を外部の entity として持たせると、商品の属性でも切れた。

## 判断の基準

- **二重計上しないこと。** 合計が元の出来事の合計と一致することを、テストで確かめられる。
- **既存の決定と合うこと。**
  - 集計は Semantic Layer に一元化する（R5）。
  - 概念とモデルは 1 対 1（ADR 0007）。
  - 生成物の計算に、LLM が書いた SQL を入れない（#46、ADR 0008）。
- **今の MetricFlow で動くこと。**

## 検討した選択肢

### 案 A: 出来事 × 値の粒度で、按分した fct を作る（採用）

- 粒度は「出来事の 1 行 × 付いた値」（例: 明細 × プロモーション）。値の無い行は、不明メンバーのキーに重み 1 で入れる。
- 重みは、1 つの出来事に付いた値の数で均等に割る。源泉に割合の列があれば、その列を出来事ごとの合計で割る（合計が 0 なら均等）。
- measure の扱い:
  - `sum` には重みを掛ける。
  - `count` は重みの合計にする。
  - `count_distinct`・`min`・`max` には重みを掛けない。
  - `average` は確定前の課題にする（按分した平均の意味が決まらないため）。
- 結合: 生成器は、BEAM で指定したブリッジの源泉と結ぶ列で、1 か所だけ一対多の結合を作る。SQL は決まった形で作る。
- 概念: ブリッジの源泉の出来事（例: 注文にプロモーションを適用する）を、オントロジーの新しい出来事の概念にし、按分した fct と 1 対 1 にする。粒度の違う fct は概念を分ける、という ADR 0007 の判断のとおりで、0007 は変えない。
- 良い点:
  - 金額の指標を、二重計上せずに出せる。
  - 合計と重み（出来事ごとに 1）を、突合テストで確かめられる。
  - MetricFlow で普通の fct として扱える。
- 悪い点:
  - fct が 1 つ増える。
  - 按分の決め方（均等か、割合の列か）を聞く必要がある。
  - 按分しない見方（全額を各値に付ける）は、合計できないので出さない。

### 案 B: ブリッジのモデルを作り、MetricFlow で結合する

- 良い点: 元の fct を変えずに、ブリッジだけを足せる。
- 悪い点:
  - 金額の合計は出せない（外部キー同士の結合を拒否される）。出せるのは、ブリッジの上の個数だけ。
  - entity の種類を誤って宣言すると、検証で見つからずに二重計上する。
  - 新しい接頭辞（`brg_`）と、概念の無いモデルが要り、ADR 0007 を変える必要がある。そのため採らない。

### 案 C: 複数の値を、配列の列に持たせる

- 良い点: fct を増やさない。
- 悪い点:
  - `unnest` のディメンションにすると、検証もクエリも通るのに、黙って行が増えて二重計上する（確かめた。181,733,642 が 194,803,775 になった）。
  - 値の無い行が消え、dim の属性とも結合できない。そのため採らない。

## 決定

案 A を採る。判断の基準の「二重計上しないこと」と「今の MetricFlow で動くこと」を優先した。一対多の結合は、BEAM で明示したブリッジの 1 か所だけを例外として許し、SQL は生成器が決まった形で作る。

## 結果

- 良い影響:
  - プロモーション別の売上のような、複数値の切り口の指標を、元の合計と一致する形で出せる。
- 悪い影響・トレードオフ:
  - 多対多の切り口ごとに、按分した fct と概念が増える。
  - 「影響のあった売上」（按分しない全額）は出さない。要求が来たら gap に記録する。
  - 既存の `raw.orders.promotion_id`（1 件目のプロモーション）と、按分した fct のプロモーションの意味が違う。ラベルで分ける（ADR 0006）。
- 後続の作業（#143）:
  - サンプルデータに、注文 × プロモーションの源泉を足す（合成。クレンジングの定義とオントロジーの概念も足す）。
  - BEAM のスキーマ（ディメンションのブリッジの指定、重みの決め方）と検査。インタビューで聞くこと（C10）。
  - 生成器: 按分した fct の SQL、突合テスト（合計の一致・重みの合計が 1）、unit test。
  - 規約の検査: `unique` の entity の列には `unique` のテストを必須にする（偽りの宣言による二重計上を止める）。
  - modeling-conventions への追記（T3）。

## 守らせ方

- 今は無い。後続の PR で、按分の突合テスト（生成した `tests/assert_<fct>_reconciles_with_source.sql`）と、`adp.generation.conventions` の `unique` の entity の検査を足す。それまでは、多対多の切り口は確定前の課題（結合できない）で止まる。
