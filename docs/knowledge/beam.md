# BEAM✲ リファレンス

インタビューエージェント（`adp.interview`）と開発者が参照する、BEAM✲ の手法の要約。出典: *Agile Data Warehouse Design*（Lawrence Corr & Jim Stagnitto）。

**人間が持ち主の知識ファイル。** この内容はそのままインタビューのシステムプロンプトに入るので、直すとプロンプトのバージョンが変わる。直す PR では eval の前後比較の表を貼る（certificate の C10）。

## 基本の考え方

- Kimball 流のディメンショナルモデリングをもとに、**アジャイルで少しずつ届ける**ことを重視する。
- 要求は「どのくらい（How many）」という**数えられる問い**に言い換える。
  - ❌ 「Web サイトでのユーザー行動を理解したい」
  - ✅ 「日次のアクティブユーザー数は？」（さらに「地域別に」「曜日別に」とディメンションを足していく）

## 7W

| W | 意味 | 落とし込み先 | 例（EC） |
|---|---|---|---|
| Who | 誰が | ディメンション | 顧客、従業員 |
| What | 何を | ディメンション | 商品、サービス |
| When | いつ | ディメンション（日付・時刻） | 注文日時 |
| Where | どこで | ディメンション | 店舗、地域、チャネル |
| How many | いくつ・いくらで | **ファクト（measure）** | 数量、金額 |
| Why | なぜ | ディメンション | プロモーション、キャンペーン |
| How | どのように | ディメンション | 支払方法、配送手段 |

## 進め方

1. **イベントの発見（モデルストーミング）**: 「誰が・何をする」のビジネスイベントを洗い出す。イベント名は `<Who> <動詞> <What>`（例: 顧客が商品を注文する）。
2. **BEAM Canvas**: 中央に How many（measure）を置き、周囲に 6W を配置する。各 W について**具体例（examples）**を聞いておく。例は後で dbt の unit test の期待値になる。
3. **粒度（grain）の確定**: fct の 1 行が何を表すかを決める。
4. **Event Matrix**: 行がイベント、列がディメンションの表。共有されるディメンション（conformed dimension）を見つけ、優先度・インパクト・工数を付ける。

## イベントの種類 → ファクトの種類

| イベント | 説明 | fct の種類 |
|---|---|---|
| discrete | 一瞬で完了する（注文など） | transaction fact |
| recurring | 定期的に測る（月末在庫など） | periodic snapshot |
| evolving | 複数の段階を経る（注文→出荷→配達） | accumulating snapshot |
