# ADR を書く・直す

ルールとテンプレートの正本は [docs/adr/README.md](../../../docs/adr/README.md)。この skill は手順だけを持つ（ルールをここに書き写さない）。承認と design-doc の更新の決まりは [certificate](../../../docs/certificate.md) の C9・T3。

## このskillを使うとき

| 場面 | すること |
|---|---|
| design-doc の Resolved issues（R<n>）を変える・覆す必要が出た | 新しい ADR（`Proposed`）を書き、design-doc を更新する（C9） |
| ライブラリ・外部サービス・構成を選ぶ、信頼の境界やデータ（個人情報・権限）の扱いを決める、複数のモジュールにまたがる約束を決める | 新しい ADR を書く |
| Open issues（O<n>）を解決する | 新しい ADR を書き、O を R に移す |
| 既存の ADR の「見直し」の条件に達した、決定の後にわかったことがある（バージョンを上げた・実際に使った結果など） | 既存の ADR の「追記」に日付付きで足す（本文は書き換えない） |
| 既存の決定を変える | 新しい ADR を書き、古い ADR を `Superseded by NNNN` にする |
| ユーザーが「ADR を書いて」「決定を記録して」と言った | 下の「書くかどうか」から始める |

**使わない（ADR を書かない）とき:** README の「書かないとき」に当たるもの（小さく閉じた決定、規約や design-doc に既に書いてあること、一時的な回避策・PoC・実験）。迷ったら、後から来た人が「なぜ」を知る必要があるかで決める。PoC の結果は、それで決めた ADR の背景に書く。

## 手順

### 1. 書くかどうか・どの形か

1. `docs/adr/README.md` を読む。
2. 関係する既存の ADR を探す（`ls docs/adr/`、`git grep -n "ADR 00"`）。同じ決定の ADR があれば、新しく書かずに追記するか置き換える（重複した ADR を作らない）。
3. design-doc の関係する R<n> / O<n> を確かめる（`docs/design-doc.md` の「Open issues」「Resolved issues」）。

### 2. 新しい ADR を書く

1. 番号: `ls docs/adr/` の最大の番号 + 1（4 桁）。
2. ファイル名: `docs/adr/NNNN-<決定を表す動詞句>.md`（英小文字の kebab-case。例: `0006-choose-warehouse-adapter.md`）。
3. README の「テンプレート」をそのまま使い、すべての節を埋める。
   - ステータスは `Proposed`。`Accepted` にしない（オーナーが決める。T3）。
   - 選択肢は 2 つ以上。採らない案にも、採らない理由を書く。
   - バージョン・計測値・費用には、いつの値か（日付・バージョン）を添える。
   - 「守らせ方」には、実在するテスト・検査を書く（`git grep` でテスト名やファイルがあることを確かめる）。新しく足すなら、同じ PR で足す。無ければ「無し」と理由。
   - 書く内容は、確かめた事実（コード・計測・ドキュメント・issue）に限る。推測で埋めない。
4. design-doc を更新する（C9）: Resolved issues に R<n> を足し（根拠の列からこの ADR を指す）、解決した O<n> を消すか R に移す。

### 3. 既存の ADR を直す

- **追記**: 末尾の「追記」に `- YYYY-MM-DD: <わかったこと・変わったこと>` を足す。背景・選択肢・決定は書き換えない。
- **置き換え**: 新しい ADR を書き（関連に古い ADR）、古い ADR のステータスを `Superseded by [NNNN](NNNN-....md)` にし、追記に理由を書く。
- **廃止**: ステータスを `Deprecated` にし、追記に理由を書く。
- 参照を追従させる: `git grep -n "ADR NNNN\|adr/NNNN"` で、design-doc・guardrails・コードのコメントの参照先（節の名前など）が古くなっていないかを確かめる。

### 4. PR

- ブランチは `docs/<issue番号>-<slug>`（issue が無ければ作る）。
- ADR の追加・`Superseded` への変更・design-doc の Resolved issues の変更は、人間が持ち主のドキュメントの中身の変更なので、PR 本文に **T3** と書き、オーナーの承認を得てからマージする。
- 敵対的レビュー（新しい subagent）では、次を観点に入れる: 事実と数値が確かめられるか、選択肢と採らない理由があるか、「守らせ方」のテスト・検査が実在するか、既存の ADR・design-doc と重複・矛盾しないか（C11）。
