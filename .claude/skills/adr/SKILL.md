# ADR を書く・直す

この skill は手順だけを持つ。正本は次のとおりで、ここに書き写さない。

- 書くとき・書かないとき、書き方、ステータス、テンプレート: [docs/adr/README.md](../../../docs/adr/README.md)
- 誰が書き・承認するか、design-doc の更新、承認が要る変更かどうか: [certificate](../../../docs/certificate.md) の C9・T3

## この skill を使うとき

1. 重要な決定をして、ADR を書くか迷うとき → 手順 1 で、README の「書くとき・書かないとき」に当たるかを判断する。当たらなければ ADR は書かない（design-doc の R を足すだけで済むこともある）。
2. design-doc の Resolved issues（R<n>）を変える・覆すとき → C9 に従い、新しい ADR と design-doc の更新。
3. 既存の ADR について、決定の後にわかったことがある・「見直し」の条件に達した・決定を変える・決定が要らなくなったとき → 手順 3。
4. ユーザーに「ADR を書いて」「決定を記録して」と頼まれたとき → 手順 1 から。

書くと決めたら、形を次で振り分ける。

| 状況 | 形 |
|---|---|
| 新しい決定 | 新しい ADR（手順 2） |
| 既存の決定はそのままで、わかったこと・変わったことがある | 既存の ADR の追記（手順 3） |
| 既存の決定を変える | 新しい ADR ＋ 古い ADR を Superseded（手順 2・3） |
| 決定が要らなくなった | 古い ADR を Deprecated（手順 3） |

## 手順

### 1. 書くかどうか

1. `docs/adr/README.md` を読み、「書くとき・書かないとき」に当たるかを判断する。
2. 関係する既存の ADR を探す: `ls docs/adr/`、`git grep -n "ADR NNNN\|adr/NNNN"`（NNNN は番号）、決定のキーワードでの `git grep`。同じ決定の ADR があれば、新しく書かずに追記か置き換えにする。
3. design-doc の「Open issues」「Resolved issues」で、関係する O<n> / R<n> を確かめる。

### 2. 新しい ADR を書く

1. 番号: `git fetch origin` の後、origin/main の `docs/adr/` の最大の番号と、開いている PR が使っている番号（`gh pr list --state open --search "adr"` と各 PR の差分）を確かめ、その次の番号（4 桁）にする。
2. ファイル名: README の「書き方」のとおり（番号と、決定を表す動詞句）。
3. README の「テンプレート」をそのまま使い、すべての節を埋める。
   - ステータスは `Proposed`。
   - 選択肢は 2 つ以上。採らない案にも、採らない理由を書く。
   - 事実は確かめたものだけを書き、確かめ方を残す（出典のリンク・コマンド・計測した日付とバージョン）。推測で埋めない。
   - 「守らせ方」には、実在するテスト・検査を書く（`git grep` でテスト名やファイルがあることを確かめる）。新しく足すなら、同じ PR で足す。無ければ「無し」と理由。
4. design-doc を更新する（C9）。Resolved issues の表は `| # | 決定 | 理由 |`。
   - 新しい決定: R<n> の行を足し、理由の列からこの ADR をリンクする。
   - R を覆す: 既存の R の行の決定と理由を直し、新しい ADR を指す。
   - O を解決する: O の行を消し、R の決定の末尾に「（O<n> を解決）」と書く。

### 3. 既存の ADR を直す

- **追記**: 末尾の「追記」に `- YYYY-MM-DD: <わかったこと・変わったこと>` を足す。背景・選択肢・決定は書き換えない。
- **置き換え**: 新しい ADR を書き（関連に古い ADR）、古い ADR のステータスを README のテンプレートの形（新しい ADR へのリンク付きの Superseded by）にし、追記に理由を書く。
- **廃止**: ステータスを `Deprecated` にし、追記に理由を書く。
- **参照の追従**: `git grep -n "ADR NNNN\|adr/NNNN"` で、design-doc・guardrails・コードのコメントの参照先（節の名前など）が古くなっていないかを確かめる。

### 4. PR とマージ

- ブランチ名・PR 本文は CLAUDE.md の作業ルールに従う（issue が無ければ作る）。
- 承認が要るかは certificate の T3 で判断し、要るなら PR 本文に「T3」と書く。
- 敵対的レビュー（新しい subagent）の観点に入れる: 事実と数値が確かめられるか、選択肢と採らない理由があるか、「守らせ方」のテスト・検査が実在するか、既存の ADR・design-doc と重複・矛盾しないか（C11）。
- オーナーが承認したら、マージの前に、ステータスを README のテンプレートの `Accepted（YYYY-MM-DD、<承認した人・場所>）` に変える commit を足す。承認の前に `Accepted` にしない。
